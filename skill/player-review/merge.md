# 合并几份玩家视角审查

> [PRK language] 交付用项目设置的语言（默认中文）。英文交付的标题和标记照工具包 docs/report-format.md 的 English 列。

谁用：主 AI（技能 player-review 第 6 步），或 API 模式的合并任务（`player_review_api.ps1` 把这一页放进任务文件）。量大时主 AI 可以派一个子代理照这一页做。

**输入**：这一轮各组的报告，和同一个文件夹的静态表。调用者（或 API 任务）列了报告路径，**只读列出来的那几份**；没列，就读文件夹里这一轮的各组报告（文件名照项目设置的 `reportNames`，不算合并报告自己），先看每份开头的日期、范围、走法、画像，和这一轮对不上的（上一轮留下的）不算，写进开头。
**输出**：同一个文件夹的合并报告（`reportNames.merged`）。
**分两级时**（API 模式按份拆分、不止一组）：第一级一组一个合并，输入是这一组拆开的几份；第二级合并各组的合并报告。任务文件里写了这是哪一级、读哪几份、写到哪，以任务文件为准。

**规矩**：只读作品，只写合并报告。不编译、不开游戏、不跑测试。不读、不列、不搜项目设置 `neverRead` 里的路径。写简单中文、短句。

## 步骤

1. **读**每一份报告：每一条问题（哪一组、编号）、「查过、没问题的」、「这次没走到的」。哪一组的报告不在（没写完、出错），记下来，写进开头。

2. **先筛掉不该报的**（挪进「误报和不报的」，写一句为什么）：
   - 玩家看不见的（只有存档里的变量、调试日志、代码写法）。
   - 宿主游戏自己的行为，作品没改也没靠它。
   - 只影响调试按钮或测试的。
   - 没有出处的：回代码找得到就补上，找不到就删。

3. **合并同一根源的**：同一处代码、同一个缺的条件、同一句台词、同一个数字引起的，合成一条。几种"玩家看到"都列上，画像和复现都留着，写上哪几组报的。严重度取最高的。建议改法合在一起，互相冲突就都写上。
   看起来不一样、其实一个原因的也要合：例如"第一次来就说'老样子'"和"连着五次都说'老样子'"都是同一行无条件加台词。

4. **核对**。要核对的：每条【可能】；每条严重和中；只有一组报的【确定】；两组结论相反的；引文核验没过的（任务里给了引文核验表的话，先看它）。轻的可以抽查。只有一组报的不能因此删掉：罕见的真问题常常只有一个人找到。

   a. 给每条写一份"主张"，只含这几样，别的都不给：
      编号｜玩家怎么遇到（步骤）｜玩家看到（原文和键）｜出处（`文件:行` + 原文）
      不给：为什么不对、反查、建议、严重度、把握、哪几组报的。写得通顺的推理会把核对的人也说服，所以不让他看。
   b. 每条派一个核对员（`player-review-checker`），并行，一条消息里一起发。它不知道别的条目，也不知道审查员怎么想的。
      不能派子代理时（API 模式的合并任务）：自己照 `{{KIT}}\agent\player-review-checker.md` 做，但先把"主张"单独抄出来，只对着主张和代码查，查完再回头看原报告。
   c. 核对员回来的结论，照下面处理：
      - 成立：标【确定】。
      - 不成立：必须带"挡住它的代码"（`文件:行` + 原文）。你打开那一行看一眼，确有其事，才挪进「误报和不报的」。没带、或对不上：按"定不了"算。
      - 定不了：留【可能】，把核对员写的"卡在哪一步、进游戏看什么"并进测试步骤。
      - 出处不实：回原报告和作品里找一次对的出处；找不到，挪进「误报和不报的」，写"出处对不上"。
   d. **方向对、细节错的留着**：核对员说"不是过夜没的，是读档才没的"，照核对员的改，不划成误报。划成误报以前，把"玩家最后看到什么"一直走到下一次存档、读档、过回合以后。
   e. 在这一条里写一行「核对：……」（结论、关键的那一处 `文件:行`）。

5. **对照旧的**：项目设置的 `previousReviews` 和最近的改动报告。
   - 审查员标了 **【回归】**的（改动报告说修了，现在还走得出来）：**留着**，算新问题，写明以前在哪报的、哪份改动报告说修了；第 4 步要核对。
   - 没标、但和以前报过的一样：回代码看现在还在不在。还在、改动报告说修了 → 改标【回归】，留着；还在、没人说修 → 标「已报，还在」，挪到「误报和不报的」后面单列一小节，不展开；不在了 → 「已修」，挪进「误报和不报的」。
   - 只凭"以前报过"不能删一条：先核对现在的代码。

   **想要但没有的（W）单独合**：它们不是 bug，不和问题混在一起排严重度。同一个缺口几组都报了，合成一条，把"谁想要"加起来（哪几组、哪几个画像）：想要的人越杂，越值得做。要核对的是"是不是真的没有"（第 4 步，主张写成"某一步没有某选项"）；核对员找到了这个选项，就挪进「误报和不报的」，并记下它要什么条件才出现。合并报告里按"想要的画像多、没有它后果重"排，每条留着"可以怎么加"。

6. **按种类多做的**：每种走法的报告有自己多写的东西（走法文件里「报告里多写什么」），合并时照着汇总。例：交互走法的条目按「宿主界面 / 系统」合并同一根源（同一处宿主代码 × 几件东西 = 一条），表里有、没人报的格子在「这次没走到的」里列出来，截图清单按宿主界面汇总成一节，写明先不跑。项目设置有 `reviewFocus` 的，合并报告「结论」里单独说一句这一块找到了什么。

7. **看看漏了哪一类**（便宜，防整类没人看）：对着下面几类问一遍"这一轮有人看过吗"，没人看的写进「这次没走到的」。信息传达错（提示、说明、文字）；数值错；一件事没正确触发下一件；状态切换错；次数和顺序错；东西该在不在；能做不该做的、不能做该做的；中途打断；能刷的漏洞；角色的逻辑；界面上的字和逻辑；玩家要点、要拖的东西点不点得中（审查员不看图：这一轮跑了 `_image_hits.md` 吗、有人顺着它查过吗）。画面、声音、镜头、碰撞、性能这几类读代码看不了，写"看不了"。（分类的出处见 `{{KIT}}\docs\references.md`。）

8. **对账**。数一数：各组报告的问题总数 = 留下的 + 合并掉的 + 误报和不报的 + 已报还在的 + 已修的。对不上：回去找少了哪一条。合并掉的每一条，在留下的那一条里要能找到它原来的"组-编号"。合并报告开头写一行这几个数。
   第二级合并：读各组的合并报告，也可以回头打开第一级的原报告（路径在各组合并报告开头）。条目的原始编号（组-份-编号）一路带着，不要重新起名以后丢了来源。

9. **编号**：严重 S1、S2……，中 M1……，轻 L1……，要{{OWNER}}定 D1……，想要但没有的 W1……（{{OWNER}}可以直接说"修 S2"）。

10. **写合并报告**（格式和审查员的一样，多几项；最后也有「索引」一节）：
   - **上一轮反馈的去向**（有上一轮的决定记录才写，放在结论后面）：把各组的这张表合起来，数一数：上一轮说修的 n 条里，解决了几条、还在的几条（【回归】，要核对）、这一轮没看到的几条。这是这一圈转得怎么样的账。
   - **玩家反馈汇总**（放在结论后面，是{{OWNER}}最先读的）：把各组报告里的「玩家反馈」合起来。
     - 一张表：玩家类型（画像）｜他会说什么（两三句，用他的话）｜对应的条目（合并后的编号）｜哪几组走过他。
     - 被核对划成误报的条目，从反馈里拿掉；【可能】的，那一句后面标"（待确认）"。反馈里不能有挂不上条目和出处的话。
     - 再列两行："**好几类玩家都会说的**"（同一条被三类以上的画像碰到）和"**只有一类玩家会说、但很重的**"。
     - "做对了的"单独列一小段：哪些地方作品回应了玩家，是哪几类玩家说的。改作品时别把这些改坏。

   - 开头：这次看了什么（范围、每组的走法和画像、每组报告的路径、缺了哪组、没算的旧报告、静态表在哪）；结论三五句。
   - 「问题一览」表多一列"哪几组报的"。
   - 每条问题照审查员的格式（严重、把握、角色、画像、怎么遇到、玩家看到、为什么不对、出处、反查、建议、测试步骤），加「核对：」和「哪几组报的：」。
   - 想要但没有的：W 编号。开头一张小表（缺口｜哪几类玩家想要｜没有它会怎样），再逐条写。
   - 要{{OWNER}}定：每条两三个选项，推荐的放第一，写清每个选项玩家那边会怎样。
   - 要进游戏确认的：【可能】的测试步骤，按角色分。写明"先不跑"。
   - 误报和不报的：第 2、4 步挪进来的，加上各组的「查过、没问题的」。
   - 这次没走到的：各组的合起来。
   - 合并报告是给没看过过程的人读的：结论放最前；不用各组内部的简称和候选编号（要用就在第一次出现时写全）；每条问题单独拿出来也要看得懂。

11. **回话**：五行以内。严重 / 中 / 轻 / 要{{OWNER}}定各几条（其中【回归】几条），误报几条，合并报告在哪。
