# 调研：怎么让"大语言模型当审查员"更准（提示词和流程）

日期：2026-11-14。范围：只读了工具包里的提示词文件，加上网查到的资料。没有跑任何审查，没有改任何别的文件。

怎么读这份文档：
- 方括号里的 **T 编号**是出处，列表在第七节。
- **【推断】**是我自己推的，没有直接出处。
- 资料大多来自"代码审查"和"安全漏洞挖掘"。它们和"只读作品、在脑子里玩"不是一回事。搬过来用的地方，都算推断，要靠评测集验证。
- 上一轮调研（`调研_审查种类.md` 4.2、4.4）说过的不重复。那里的来源编号是 K 开头。

## 一、一页结论

按"效果大 × 改起来便宜"排。前五条最值得先做。

1. **先把评测集做出来，再改提示词。** 用 `examples\tea-stall` 加一张答案表、几个"诱饵"（看着像 bug 其实不是）、一个干净版本。每版提示词跑三次，算检出率和误报数。没有它，后面每一条改了是好是坏都不知道。[T15][T18][T33][T41][T58]
2. **把"回代码核对"从合并里拆出来，交给独立的核对员。** 核对员只看到"主张"（怎么遇到、玩家看到什么、出处），看不到审查员的推理。判"不成立"必须写出挡住它的那段代码；定不了就留【可能】。[T43][T44][T9][T19][T8][T16]
3. **每条发现必须带原文引用，交报告前逐条重开出处核一遍；对不上就撤。** 再加一个几秒钟的脚本，机械地检查"这个文件这一行真有这句话"。[T3][T1][T15]
4. **重排任务文件。** 审查员说明放进系统提示；长的材料放前面；"这次的任务"和"交付要求"放最后；用标签把几类内容分开。[T1][T7][T13]
5. **系统提示里放三到五个完整例子**：一条真问题、一条被代码挡住的候选、一条【可能】、一条【设计】。例子比抽象规则管用。[T1][T13][T16]
6. **画像只管"手"，不管"脑"。** 画像决定玩家做哪些操作；分析和下结论照审查员的全部本事做。画像里留动作清单，不加性格形容词。研究说角色提示不提高准确度，"装不懂"的角色还会拉低。[T22][T26][T24][T30]
7. **走的时候写草稿文件**：覆盖表（哪趟走完了）、候选清单、账本。报告从草稿整理出来。覆盖表没走完的，主 AI 补派。[T1][T13][T17][T2]
8. **把{{OWNER}}对每条发现的决定记下来**（修 / 不是 bug / 是设计 / 误报）。这是最真的精确率数据，也是以后例子的来源。[T34][T42][T56][T15]
9. **加"作品地图"**：先派一个代理把角色、标记、物品、结局、数值整理成带出处的表，各审查员共用。地图是线索，不是结论。[T53][T17][T12][T48][T38]
10. **把子代理的配置写明**：模型、effort、最多几轮、不带 CLAUDE.md；无界面模式加 `--bare`。effort 在评测集上试过再定。[T6][T7][T2]

不建议加的：多代理辩论、"只有一组报就删"的投票、让审查员自己打置信度分数、向量检索、给审查员加"专家"头衔、整份报告强制 JSON。理由在 3.7。

## 二、对现有提示词的逐个诊断

### 2.1 `agent\player-bug-reviewer.md`（审查员系统提示）

**写得好的，留着**

- 语气平实，没有大写和"必须必须"。官方现在明说：堆强调词只会让模型把规则用过头。[T8]
- "算不算问题"先要求说清"对照的是什么"，说不出就不报。这是把判断标准写明白了。[T1]
- "不报"的清单。Anthropic 自己的安全审查提示也是靠一张"硬排除"清单压误报。[T19]
- "反过来查"和"走到底"。方向对。官方的说法是：叫审查员找问题，他总能找到点什么，所以要有反向的一步。[T8]
- 把握分三档，【确定】的定义是**证据标准**（每一步都有出处），不是让模型说"我有几成把握"。这点很重要：模型自己说的置信度普遍偏高。[T54]
- "静态表是线索，不是结论"。[T36][T40]
- 【回归】的处理。
- 报告有固定结构，有"查过、没问题的"和"这次没走到的"两节。让模型有地方说"没看""不知道"，能少编。[T3]

**可以改的**

**（1）"你是谁"把两件事混在一起了。** 现在写"你站在玩家那边"。玩家视角用来决定**看什么、走哪条路**是对的。但研究说，给模型一个"水平低"的角色（外行、小孩），答题准确度会掉 [T26]；给社会身份类角色，推理题也会掉，模型还会"替角色"说自己不会 [T24]。所以要明说：扮玩家只扮到"做什么操作、看得见什么"为止，回代码找原因时是审查员。

改后草稿：

```
# 你是谁

你是「玩家视角审查」的审查员。你有两件事，分开做：

1. **替玩家走。** 走法和画像告诉你这个玩家做哪些操作、看哪些字、不看哪些字。
   这一步你只用玩家看得见的东西：屏幕上来了谁、台词原文、按钮上的字、东西、钱、
   确认窗、消息、日志和图鉴、设置窗口、物品说明、谁再也不出现了。
2. **替作者查。** 玩家那边看着不对劲了，你回代码、数据、文本里找原因。
   这一步你是细心的审查员，用全部本事：把相关的文件打开读，把条件一条一条走通。

画像只决定第 1 件事（走哪条路、做什么操作）。它不决定你查得多细。
画像写"不读字""马虎"，意思是这个玩家会跳过提示；不是让你少读代码。
```

**（2）"不猜"太短，没说怎么做到。** 官方给的办法很具体：先摘原文再下结论；写完以后给每个结论找一句支持它的原文，找不到就撤掉 [T3]。还有一条专门给读代码的代理：没打开过的代码不要下结论 [T1]。

改后草稿（替换硬规矩第 4 条）：

```
4. **有原文才算数。**
   - 每个结论都要有出处：`文件:行`，加上那一行的原文（照抄，不改字）。文本表写键和原文。
   - 没打开读过的文件，不对它下结论。记不清就再打开一次。
   - 宿主游戏怎么做，你看不到代码的，写"看不到"，标【可能】。
   - 说不清、查不到的，写"不知道"或"没查到"。这比猜一个答案有用：
     猜错的一条会让{{OWNER}}白花时间，也会让别的条目不被信任。
```

**（3）"先读"第一句"读够就停，别整本整本地读"和后面要求的"列全集""走到底"有冲突。** 官方现在的说法是：上下文窗口够大，很少用完；该省的是无关内容，不是相关内容 [T8]。但输入越长，模型用得越不均匀，这也是真的 [T52][T51]。所以改成：背景材料按需读，**和结论有关的必须读到那一行**。

改后草稿（替换"先读"的标题行）：

```
## 先读（按顺序）

背景材料（设定、说明、设计稿）：读和范围有关的小节，够用就停。
和结论有关的代码、数据、文本：不能省。写进报告的每一步，对应的那几行都要打开读过。
有作品地图（`{{MAP}}`）就先读它，再按它指的位置去读原文件。地图是线索，不是结论。
```

**（4）没有"工作顺序"。** 现在"反过来查"是一段说明，不是一个阶段。业界做得好的流程都是分阶段的：先找候选，再逐条验证，再排序 [T9][T19][T44]。研究也说：模型只靠自己重新想一遍，纠不了自己的错，有时还越改越错 [T46]；管用的是回到外部证据，而且验证时不要带着原来的草稿 [T45]。

加一节草稿（放在"清单"前面）：

```
## 工作顺序（五步，别跳）

1. **读**：照「先读」。
2. **走**：照走法走。看到不对劲，先记进草稿文件的"候选"，写一句话加出处。这时候不下结论。
3. **查**：走完一趟，回头一条一条查候选。每条都做「反过来查」和「走到底」。
   查的时候重新打开出处，不凭刚才的印象。
4. **核引文**：写报告以前，把每条要报的问题里的每个 `文件:行` 再打开一次，
   确认原文一字不差、行号没错。对不上的：改对；改不对：撤掉这一条，记进「这次没走到的」。
5. **写**：照「报告」的格式写。

候选被挡住是正常的。一趟走下来，候选里有一半以上被挡住，不算白走：
写进「查过、没问题的」，{{OWNER}}就知道这些地方看过了。
```

**（5）清单 A–K 太长，像一张"边角情况大全"。** 官方建议：别往提示里塞一长串边角规则，挑几个有代表性的例子更好 [T13]。但清单对"防漏"有用，我拿不准该不该砍。【推断】折中：系统提示里只留每类一行的标题；细问句挪到 `{{KIT}}\method\清单.md`，走法文件的最后一步再让他去读。这样每种走法只在补漏时才把清单读进来。**这一条先在评测集上对比再决定。**

**（6）没有例子。** 这是最缺的一块。官方说三到五个例子，要贴近真实用法、要有差别（别让模型学到无关的规律）、用标签包起来 [T1]。Anthropic 自己调"评审员"代理时，也是靠例子把它的松紧校准的 [T16]。

加一节草稿（放在"报告"后面；内容是编的，不对应任何真实作品）：

```
## 例子（写法和松紧照这个来；内容是编的）

<examples>

<example 类型="真问题，【确定】">
### M1 第一次见面，他说"还是老样子"
- 严重：中　把握：【确定】　角色：角色甲　画像：1 好心人
- 怎么遇到：
  1. 第 1 回合，角色甲第一次来。玩家以前没见过他。
- 玩家看到：「还是老样子。」（`text\zh.csv:41` 键 `jia_greet_2`）
- 为什么不对：玩家以为这是第一次见面；台词假定以前来过。对照：前后不一样。
- 出处：`data\jia.json:12` 原文 `"greet": ["jia_greet_2"]`（没有"来过几次"的条件）
  → `text\zh.csv:41` 原文 `jia_greet_2,还是老样子。`
- 反查：全作品搜了 `visitCount`、`firstVisit`、`jia_greet_1`。
  `visitCount` 只在 `data\yi.json:30` 用到，管的是角色乙。没挡住。
- 建议：给这句加"来过至少一次"的条件；或第一次用 `jia_greet_1`。
</example>

<example 类型="候选被挡住，不报">
候选：没有红钥匙也能进仓库。
查：`logic\door.json:8` 原文 `"requires": ["key_red"]`。条件在。
再查有没有别的门进仓库：搜 `"to": "storeroom"`，只有这一处。
结果：不报。写进「查过、没问题的」：
「没钥匙进仓库：被 `logic\door.json:8` 的 requires 挡住；没有第二个入口。」
</example>

<example 类型="【可能】">
### M2 背包满了，他送的信可能丢了
- 严重：中　把握：【可能】　角色：角色乙
- 怎么遇到：1. 背包放满。2. 第 5 回合角色乙来，送信。
- 玩家看到：「这封信你收好。」（`text\zh.csv:77` 键 `yi_letter`）；背包里没有信。
- 出处：`data\yi.json:44` 原文 `"give": "item_letter"`（没有"放不下怎么办"）
- 定不了的那一步：背包满时 `give` 怎么处理，是宿主游戏的代码，这里看不到。
- 反查：作品里搜了 `inventoryFull`、`onGiveFail`，没有。
- 测试里怎么复现：背包放满 → 跳到第 5 回合 → 让角色乙来 → 检查背包和地上有没有信。
  要确认的是：信是掉在地上、进了邮箱，还是没了。
</example>

<example 类型="【设计】">
### D1 拒绝他以后，这条线再也没有后话
- 把握：【设计】
- 代码和设计稿一致：`notes\bing.md:20` 原文「拒绝后不再出现」。
- 玩家那边：拒绝按钮上只有「不行」两个字，事先没有提示这是最后一次见他。
- 选项：1.（推荐）拒绝前加一句预兆的台词；玩家知道这是诀别。
  2. 不改；玩家会觉得这条线断了。3. 以后别的角色提一句他的去向。
</example>

<example 类型="不要这样写">
「角色甲的对话逻辑可能有问题，建议检查。」
没有玩家的操作步骤，没有原文，没有出处。这样的一条不要写进报告。
</example>

</examples>
```

**（7）没有说"做完才停"和"上下文会被压缩"。** 新一代模型在长任务里有时会提前收尾：列出"还剩什么"就停。官方给了一段话来压这个毛病，在较低 effort 下更需要 [T2]。还提醒：如果运行环境会自动压缩上下文，要告诉模型，并让它把状态存到文件里 [T1]。我们的报告里正好有一节「这次没走到的」，它给了模型一个体面的地方提前收工。【推断】

加一节草稿：

```
## 做完才停

- 任务里给你的每一趟「画像 × 线」（或每一个必经点、每一格），都要走到，或者写明为什么走不了。
  「这次没走到的」是给**走不了**的地方用的（要进游戏看、材料缺了），不是给"没时间了"用的。
- 读文件报错、搜不到、静态表不在：先想办法（换个搜法、自己跑静态脚本），不要因此停下。
- 你的上下文快满时会被自动压缩，你可以接着做。所以随时把进度写进草稿文件：
  压缩以后，先读草稿文件，再接着走。
```

**（8）"只写报告文件"和草稿文件冲突。** 要改一个字眼。

```
1. **只读。** 不改项目里的任何文件。你只写两个文件：调用者给你的报告文件，
   和它旁边的草稿文件（报告文件名后面加 `.草稿.md`）。静态脚本会写它们自己的输出，可以跑。
```

加一节草稿（"草稿文件"）：

```
## 草稿文件（边走边写）

三块，都是给你自己和合并的人看的，不用写得好看：

1. **覆盖表**：一行一趟。| 画像或格子 | 线 | 走到哪 | 状态：没开始 / 在走 / 走完 / 走不了（原因） |
2. **候选**：一行一条。| 编号 | 一句话 | 出处 | 状态：待查 / 报 / 被挡住（哪段代码） / 定不了 |
3. **记下的事实**（走法要记账时用）：谁活着、谁知道什么、东西在谁手上、哪些标记是真的。每条带出处。

报告里的「问题」「查过、没问题的」「这次没走到的」，从这三块整理出来。
候选表里每一条都要有去处，不能凭空少掉。
```

出处：结构化的状态用表或 JSON，进度用自由文字 [T1]；让代理在上下文之外记笔记 [T13]；长任务靠"清单文件 + 进度文件"接力 [T17]。

**（9）报告格式小改。** "玩家看到"和"出处"里都加原文（上面例子里已经这样写）。报告最后加一小块机器好读的索引，方便引文核验脚本、合并、评测对答案用。不要把整份报告改成 JSON：研究说强制格式会拉低推理表现 [T55]，官方也建议自由推理和结构化输出分开。

```
## 索引（最后一节，给脚本读；一行一条，用竖线分开）
编号 | 严重 | 把握 | 文件:行 | 那一行的原文（照抄）
M1 | 中 | 确定 | data\jia.json:12 | "greet": ["jia_greet_2"]
M1 | 中 | 确定 | text\zh.csv:41 | jia_greet_2,还是老样子。
```

**（10）不要让审查员在报告里写"我的思考过程"。** 新模型的官方指南说：要求把内部推理写进回答的提示，应该删掉，有可能被拒 [T2][T1]。我们现在的格式要的是**证据**（步骤、原文、出处），不是思考过程，没问题。以后加字段时注意别写成"写出你的推理"。

**（11）frontmatter。** 子代理文件支持 `model`、`effort`、`maxTurns`、`omitClaudeMd` 等字段；拼错的字段会被悄悄忽略 [T6]。子代理不继承主对话，但会自动带上 CLAUDE.md 文件 [T6]。机器上或项目里的 CLAUDE.md 和审查无关时，会白占上下文，也让不同机器的结果不一样。【推断】建议：

```
---
name: player-bug-reviewer
description: （不变）
tools: Read, Grep, Glob, Bash, Write
model: inherit
effort: high
maxTurns: 200
omitClaudeMd: true
---
```

`omitClaudeMd` 我只在官方页面的字段列表里见到，没读到细节，用之前请查一下（见第六节）。项目规矩已经由 `rulesFile` 和 `projectRules` 给了，不靠 CLAUDE.md。

### 2.2 `api\task_template.md`（无界面模式的任务文件）

**写得好的**：开头就说清"没人可问，拿不准写进报告"。字段齐。

**可以改的**

**（1）顺序反了。** 现在是：这次的任务 → 审查员说明（长）→ 走法（长）。官方建议：长材料放上面，具体要求放最后；在多份长材料的测试里，把提问放最后，质量最多能好三成 [T1]。我们的"长材料"是说明不是数据，所以这条算【推断】，但改起来不花钱。

**（2）审查员说明应该进系统提示。** 子代理模式下，代理文件的正文就是系统提示 [T6]。无界面模式现在把它贴在用户消息里，两种模式不一样。命令行有 `--append-system-prompt-file` [T7]。脚本现在没用它（我只看了 `run_api_task.ps1` 里用到哪些参数：`--output-format`、`--verbose`、`--model`、`--disallowed…`、`--max-turns`、`--permission-mode`、`--allowed…`）。

**（3）没有标签分块。** 一份提示里混着规矩、走法、变量，用标签包开能少误读 [T1][T13]。

**（3）加一段"画像管什么、不管什么"**（和 2.1 的"你是谁"配套）：

### 2.7 `skill\player-review\merge.md`（合并和核对）

**写得好的**

- 先筛、再合并同一根源、再核对。**先去重再核对**正是业界建议的顺序：不去重，核对的钱会花在同一个问题的很多份上 [T44]。
- "划成误报以前，走到底"和"审查员的结论错了一半，方向可能是对的"。很少有流程想到这一点。
- "只凭'以前报过'不能删一条"。
- 第 7 步"看看漏了哪一类"。便宜的覆盖检查。
- 只有一组报的【确定】要核对，而不是直接删。有的产品早期用"只有一遍报就丢掉"的投票，后来放弃了这套固定流程 [T34]；罕见但真的问题，往往只有一遍能找到 [T32][T33]。

**可以改的**

**（1）核对的人看得到审查员的推理。** 现在第 4 步让合并的人"看'反查'那一行"。问题：一段写得通顺的推理，会把读的人也说服 [T44]。几份实践都用"信息不对等"：反驳的人只看到主张本身，看不到找的人怎么想的 [T43][T44]。官方也说：新开的审查者有用，正因为它没看过产生结论的那段推理 [T8]。Anthropic 自己的两套审查（托管的代码审查、安全审查提示）都是"并行找 → 单独一步验证 → 去重排序"，安全审查那套是每条发现开一个并行子任务来过滤 [T9][T19]。

**（2）没有"定不了"以外的保护。** 反驳流程有个已知的坑：它只会杀，不会救。有研究记录了一条真问题被一致杀掉，靠人才救回来 [T43]。所以我们的规矩应该是：**判"不成立"必须引出挡住它的代码**；引不出，只能判"定不了"。给评判的模型留一个"不知道"的选项，也是官方的建议 [T15]。

**（3）没有对账。** 两级合并时，条目有可能悄悄少掉。多代理系统常见的失败之一就是核对环节出问题 [T47]；官方也提醒子代理之间转述会像传话游戏一样走样，办法是让原件落在文件里、只传引用 [T12]。

改后草稿（替换第 4 步）：

```
4. **核对**。要核对的：每条【可能】；每条严重和中；只有一组报的【确定】；两组结论相反的；
   引文核验没过的。轻的可以抽查。

   a. 给每条写一份"主张"，只含这几样，别的都不给：
      编号｜玩家怎么遇到（步骤）｜玩家看到（原文和键）｜出处（文件:行 + 原文）
      不给：为什么不对、反查、建议、严重度、把握、哪几组报的。
   b. 每条派一个核对员（`player-review-checker`），并行。它不知道别的条目，也不知道审查员怎么想的。
      不能派子代理时（API 模式的合并任务）：自己做，但先把"主张"单独抄出来，
      合上原报告，只对着主张和代码查。
   c. 核对员回来三种结论，照下面处理：
      - 成立：标【确定】。
      - 不成立：必须带"挡住它的代码"（文件:行 + 原文）。你打开那一行看一眼，确有其事，
        才挪进「误报和不报的」。没带、或对不上：按"定不了"算。
      - 定不了：留【可能】，把核对员写的"卡在哪一步、进游戏看什么"并进测试步骤。
   d. 核对员说"方向对、细节错"（例：不是过夜没的，是读档才没的）：照核对员的改，留着。
   e. 在这一条里写一行「核对：……」（谁核的、结论、关键的那一处 文件:行）。
```

加一步（放在"写合并报告"之前）：

```
8.5 **对账**。数一数：
    各组报告的问题总数 = 留下的 + 合并掉的 + 误报和不报的 + 已报还在的 + 已修的。
    对不上：回去找少了哪一条。合并掉的每一条，在留下的那一条里要能找到它原来的"组-编号"。
    合并报告开头写一行这几个数。
```

两级合并加一句：

```
第二级合并：读各组合并报告，也可以回头打开第一级的原报告（路径在各组合并报告开头）。
条目的原始编号（组-份-编号）一路带着，不要重新起名以后丢了来源。
```

**（4）合并报告是给没看过过程的人读的。** 官方给新模型的建议：读最后报告的人没看过工具调用和文件，报告要自己能看懂；结论放最前；不用干活时临时起的简称 [T2]。现在的格式基本符合。加一句：

```
合并报告里不用各组内部的简称和候选编号（例："候选 7""甲线第二趟"）。
要用就在第一次出现时写全。每条问题单独拿出来也要看得懂。
```

## 三、建议新加的环节

### 3.1 作品地图

**做什么**：审查开始前，派一个代理把作品整理成一份结构化的表，带出处。后面的审查员、核对员都先读它。

**为什么**
- 现在每个审查员都要自己从头理一遍"有哪些角色、标记、物品、结局"。理得不一样，结论就对不上；并行的子代理各自带着没说出口的假设，是多代理最常见的毛病 [T48]。
- 给模型一张"仓库地图"（文件、关键符号、定义所在的行），是成熟的做法 [T53]。
- 长任务的官方做法是：第一个代理只搭架子，产出一份结构化的清单文件，后面的代理照清单干 [T17]。
- 软锁走法的"必经点表"、账本走法的"事实"、全收集画像的"全集"，都能从地图起步，不用各列各的。
- 注意：官方现在说上下文很少用完 [T8]。所以地图的好处主要是**一致**和**不漏**，不是省上下文。【推断】

**风险**：地图错了，所有审查员一起错。没有集中核对的并行结构会把错误放大 [T49]；一群同一种模型的代理会共用同一个错的假设 [T43]。对策：地图每一行带出处；写明"线索不是结论"；用它下结论前回原文件；引文核验脚本也检查地图。

**提示词草稿**（新代理 `player-review-mapper`；只读，只写地图文件）：

```

你给一个作品画"地图"：把代码、数据、文本里的事实整理成表，给后面的审查员用。

6. **数值**：价钱、预算、门槛、次数上限。| 名字 | 值 | 谁用它 | 出处 |

   只列条件和出处，不抄全文。
8. **互相提到**：| 说话的人 | 提到谁 | 键 | 条件 | 出处 |
```

### 3.2 核对员

**做什么**：一个专门的只读代理。输入是一条"主张"，输出是"成立 / 不成立（附挡住它的代码）/ 定不了"。它看不到审查员的推理，看不到别的条目。

**为什么**
- 自己评自己会偏松：代理给自己的活打分时倾向于说好话；换一个独立的评审也仍然偏松，要专门往"多疑"那边调 [T16]。
- 模型只靠自己重想，纠不了错 [T46]；带着原草稿去验证，会被草稿带偏，分开回答验证问题更好 [T45]。
- 实践数字（都是安全领域，自己报的，没有独立复核）：反驳阶段杀掉了六到九成的原始候选 [T44]；另一份是约八成 [T43]。托管的代码审查说工程师标为"不对"的发现不到 1% [T20]（厂商自己的数字，对象是代码改动，不是整个作品）。
- 静态分析的误报用"模型 + 程序分析"裁决，一项工业研究里消掉了九成以上的误报，每条几秒到一两分钟 [T40]。
- 反过来的教训：数人头不管用。很多代理意见一致，不说明是真的；能改变把握的是证据 [T43]。辩论的收益大部分其实来自投票本身 [T50]。

**提示词草稿**（新代理 `player-review-checker`；`tools: Read, Grep, Glob`，不给 Write，结果直接回话）：

```
# 你做什么

你是核对员。有人说作品里有一个玩家会碰到的问题。你回作品里查：这件事会不会真的发生。
你没看过他是怎么想的，只看到下面的"主张"。这是故意的：你要自己走一遍。

规矩：只读。不编译、不开游戏、不跑测试。不读、不列、不搜 `neverRead` 里的路径。
每一步都写 `文件:行` 和那一行的原文。没打开过的文件，不对它下结论。

# 怎么查（按顺序）

1. **核出处**：打开主张里的每一处 `文件:行`。那一行是不是真有这句原文？
   对不上：先在附近和全作品找这句话。找到了，用对的位置接着查；找不到，结论是"出处不实"，停。
2. **正着走**：从"玩家怎么遇到"的第一步，走到"玩家看到"的那一句。
   每一步要的条件是什么？这些条件在同一局里能同时成立吗？
3. **专门找挡住它的东西**。至少查这几处，查了什么都写下来：
   - 这一段代码或数据上游的条件、只触发一次的标记。
   - 别的角色、公用框架里管同一个标记、同一件物品、同一个文本键的地方（全作品搜名字）。
   - 数据里的条件字段、默认值。
   - 说明文字或台词里有没有事先的警告（有警告的死路可能是故意的）。
   - 作品是模组时：宿主游戏会不会兜底。看不到宿主代码，就写"看不到"。
4. **走到底**：这件事发生以后，到下一次存档、读档、过回合，玩家最后看到什么？
   主张说的后果，会不会只对了一半（例：不是过夜没的，是读档才没的）？

# 结论（三选一）

- **成立**：第 2 步每一步都有原文，第 3 步没找到挡住它的东西。
- **不成立**：你找到了挡住它的代码或数据。必须写出 `文件:行` 和原文。
  写不出这一行，就不能选"不成立"。
- **定不了**：有一步要看宿主游戏、时机或画面。写清是哪一步、进游戏要看什么。

主张写得通顺，不等于它是真的。你觉得它不像真的，也不等于它是假的。只看你打开的那几行。
方向对、细节错的，选"成立"，并写出对的细节。

# 回话格式

编号：…
结论：成立 / 不成立 / 定不了 / 出处不实
走过的路：（一步一行：做什么 → `文件:行` 原文）
找过的挡板：（搜了什么词、看了哪几处、各是什么结果）
关键的一处：`文件:行` 原文（"不成立"时是挡住它的那一行）
更正：（主张里哪里说错了；没有就写"无"）
进游戏要看的：（"定不了"时写）
```

**和实践不一样的地方（故意的）**：有的流程把"拿不准"默认判成"驳回" [T44]。我们默认留【可能】。原因：{{OWNER}}要的是少漏，而且我们没有"进游戏跑一下"这个最后的证据关口；那些流程的最后一关是真的运行 [T43][T44][T21][T35]。【推断】

**多花多少**：每条待核对的一次短运行，可以并行。先去重再核对能省很多 [T44]。可以给核对员用和审查员不一样的模型：有研究用另一家的模型当最后一道评审，多杀掉了少量前面放过的条目 [T43]；官方评测文档也建议打分的模型和产出的模型不同 [T5]。要不要换，在评测集上比。

**出处**：[T43][T44][T45][T46][T16][T9][T19][T8][T40][T50]

### 3.3 评测集（把 `examples\tea-stall` 做成的话）

**做什么**：一套固定的作品 + 答案表 + 打分办法。每次改提示词、换模型、加环节，都跑一遍，看检出率和误报有没有变好。

**为什么**
- 官方的话：没有评测，就只能凭感觉；二三十道题就可以起步，题目从真实失败里来；两个懂行的人对同一个结果要能判出一样的过或不过 [T15][T12]。
- 同一个提示、同一份代码，跑三次，发现条数是 3、6、11，只有一部分重合 [T33]。同一个已知漏洞，一百次里只找到 8 次 [T32]。所以**跑一次不算数**。
- 新模型不一定更好：一个代码审查基准上，新一代模型反而不如上一代 [T41]。指南里对某个模型管用的写法，换模型要重测 [T1][T2]。
- 很多看着有道理的改动，一测是退步 [T34]。

**怎么做（七步）**

1. **答案表**。放在审查员读不到的地方（工具包之外，或加进 `neverRead`）。评测要防"偷看"：官方举过代理从上一轮留下的记录里拿到答案的例子 [T15]。上一轮的 `review_out` 也要挪走或列进 `neverRead`。
   一行一个埋的问题：编号｜类型（清单 A–K 的哪一类）｜在哪（文件:行）｜玩家看到什么｜严重度｜哪种走法应该找到｜静态表能不能直接抓到。
   现在有 7 处（文本 5、数据 2）。太少，而且偏文字类。

2. **补题到二三十个，各类都有**。现在缺：软锁、台词和事实对不上（要走分支才看得出）、数值漏洞、时间撞车、存档读档、互相提到。例子游戏没有代码，可以加一小段行为数据或规则表来承载。

3. **加诱饵（反例）**。看着像 bug、其实不是的：被别处条件挡住的"无条件台词"；有事先警告的故意死路；设计稿里写明的不公平。官方强调评测要两边都有：该报的和不该报的；只测一边，会把代理调成一边倒 [T15]。代码审查基准也是一半有问题、一半干净 [T41]。
   诱饵用来量误报，也用来量核对员（它该判"不成立"并指到挡板）。

4. **做一个干净版，再用"埋 bug"的办法出变体**。从干净版出发，脚本每次埋进一两个问题，生成一批变体。往真实的改动里人工埋缺陷，再看工具能不能找回来，是现在代码审查基准的常见做法 [T58]；测试领域的"变异"也是同一个思路，可以让模型帮着造 [T57]。
   好处：题多、便宜、能留一批从没用来调提示词的"留出题"，防止把提示词调成只会做这几道 [T14]。
   埋完要人看一眼：有的变体其实不改变玩家看到的东西（"等价变体"），要剔掉 [T57]。

5. **对照层分两版跑**。带"去查 / 觉得不对劲"的原版，和去掉这两栏的版本。原版会把答案指给审查员（见 2.4）。两版的差，就是"对照层写得细"值多少。【推断】

6. **打分**。
   - 每个配置跑至少 3 次 [T33][T15]。
   - **检出率**：每个埋的问题，3 次里找到几次。再看"至少一次找到"和"三次都找到"两个数 [T15]。
   - **误报**：报出来、对不上答案表的条目。先人看：有的是没埋但真的问题，补进答案表 [T58]；剩下的才算误报。诱饵被报了几次单列。
   - **把握准不准**：标【确定】的里面有几条是错的。这是最伤信任的一种错。
   - **核对员**：真问题被它判"不成立"几次（错杀）；诱饵被它判"成立"几次（漏杀）。
   - **钱和时间**：每次运行的花费（日志最后那行 JSON 里有）。
   - 对答案可以让模型来做（"这条发现说的是不是答案表里的这一条：位置对、现象对"），再抽查。两个基准都这样做，和人的一致度约九成 [T41][T58]。题少的时候人对更快。给评判的模型留"不确定"选项，判过或不过，不打 1–5 分 [T15][T56]。
   - 报告最后的「索引」一节就是为这一步准备的：按 文件:行 先粗配，再看现象。

7. **比较两个版本**。同一批题、逐题比差值，比各算一个总分再比要准 [T18]。题少时只看得出大差别 [T12][T18]；差一两题不要当真。已经稳定能找到的题，转成"回归集"，以后每次改动都不该掉 [T15]。每次都翻几份没找到的报告和日志，看是审查员的错还是题的错 [T15][T14]。

**这个评测集量不到的**
- 例子太小、没有代码：量不到长上下文下的表现，量不到对宿主游戏的猜测。[T33] 提醒：小而干净的题会高估表现。要有一个中等大小的第二套题。可以是真作品的一份拷贝里埋题（要{{OWNER}}同意）。【推断】
- 埋的 bug 可能带着模型的"口音"，另一个模型特别容易或特别难找到 [T58]。
- 真实世界的信号靠 2.3 的"决定记录"补。

**多花多少**：答案表和诱饵是一次性的人工。每次评测 = 组数 × 3 次运行。先只跑默认的那几组。

**出处**：[T15][T18][T12][T14][T33][T32][T41][T58][T57][T56][T34]

### 3.4 引文核验脚本

**做什么**：一个静态脚本。读报告最后的「索引」一节，逐行检查：这个文件存在吗、这一行是不是这句原文（去掉首尾空白后比对；行号差几行以内算"行号偏了"）。输出一张表：对 / 行号偏了 / 找不到。

**为什么**：出处写错、行号编造是最便宜就能抓到的一类错。官方把"写完以后给每个结论找原文，找不到就撤"列为减少幻觉的基本办法 [T3]；能用代码判的就用代码判，快、便宜、每次结果一样 [T15][T5]。把规则交给程序强制，比写在提示里请求更可靠 [T8]。

**多花多少**：几秒钟，不花钱。要写一个小脚本，登记进静态表。

**提示词这边的配合**：2.1（9）的「索引」一节。

**出处**：[T3][T15][T5][T8]。脚本本身是【推断】，没有照搬的现成例子。

### 3.6 重点范围跑两遍（可选）

**做什么**：{{OWNER}}最在意的那一块（例：主线软锁），同一组派两个审查员，换一换读的顺序或拆分方式。两份的发现**取并集**，一起交给核对员。

**为什么**：同一提示多跑几次，会冒出新的发现 [T33]；把十份审查合起来，一个基准上找回的比例翻了一倍多 [T41]；有人干脆把模型当成"从一个分布里抽样"的工具来用 [T32]；安全研究里也主张多条独立的尝试，而不是一条路走到黑 [T35]。

### 3.7 我觉得不值得加的

- **多代理辩论**。收益主要来自投票，不是来自讨论 [T50]；一个会说话的代理能压过多数 [T43]。花钱多，不如独立核对。
- **"只有一组报就删"的投票**。压误报，但也压掉罕见的真问题。用过的团队后来换了做法 [T34]。
- **让审查员给自己打置信度分数（0–100）**。模型口头说的置信度偏高 [T54]。现在按证据分档的做法更好。要分数，让核对员按"有没有找到挡板"来给。
- **给审查员加"资深测试专家"之类的头衔来提高准确度**。两项研究都没发现角色头衔稳定提高准确度 [T22][T26]。官方文档仍然说一句角色能定调子和关注点 [T1]，这个作用现在的"你是谁"已经有了。
- **向量检索 / 预先建嵌入索引**。官方的方向是让代理用文件路径和搜索"用到再取" [T13]；我们的作品是代码加数据表，Grep 就够。作品地图是更合适的"索引"。
- **整份报告强制 JSON**。格式限制会拉低推理 [T55]。保留 Markdown，加一小节索引就行。
- **"仔细想""不要偷懒""务必彻底"之类的话**。官方说这些话现在更可能引起过度工作，深浅该用 effort 来调 [T8]。
- **再加一层规划代理**。见 2.3（4）。
- **在提示里给模型看 token 预算**。官方测试里，拿掉预算反而省钱、表现一样 [T2]。

## 四、persona 提示有没有用

**研究怎么说**

1. **角色不提高答题准确度。** 一项研究试了 162 个角色、2410 道事实题、四类模型：加角色和不加比，总体没有提高；每题都有某个"最好的角色"，但事先挑不出来，和随机差不多 [T22]。另一份报告在更难的题上重做：对口的专家角色基本没差别，不对口的有时更差，"外行、小孩"这类低知识角色明显更差 [T26]。
2. **早期也有正面结果。** 有论文在 12 个推理基准上报告角色扮演提示有提高 [T23]。后来的研究在另一个模型上看到 12 个数据集里 7 个变差，并指出角色选不好会帮倒忙 [T25]。合起来看：效果不稳，和模型、题目有关。
3. **社会身份类角色会带出偏差。** 给模型一个人群身份，推理题成绩会掉，有的掉得很多；模型还会"替这个身份"说自己不会 [T24]。
4. **模拟某一类人，保真度有限。** 用模型代替真人被试，会把一个群体写得很平、很像外人眼里的样子 [T27]；越是照标签演，越容易演成夸张的漫画 [T29]。只给人口学描述的代理，比给了两小时访谈内容的代理差一截 [T28]。上一轮查到的"合成用户爱说好话、会说自己做完了"（K18）也是这一类。
5. **什么样的画像会让行为真的不一样。** 一项研究固定动作集合，只换故事外壳和画像：故事外壳解释的行为差异是画像的 5 到 31 倍；画像的效果里，能跨场景保持的那部分来自**写了具体动作的描述**，把动作词拿掉，一致性掉了 95% [T30]。上一轮的 K16 也是按行为维度（偏点击、偏输入、输入合不合法）定画像。还有一篇说光靠提示词调出来的"不耐烦的用户"不够像，我只看到搜索摘要，不展开 [T31]。

**对我们的画像写法意味着什么**

- **画像的用处是"多样"，不是"更准"。** 它让不同审查员走不同的路。这和上一轮的结论一致。不要指望"扮演玩家"让找 bug 更准；准不准靠证据规矩和核对。【推断】
- **现在的写法方向是对的。** 通用层的"怎么玩 / 不看 / 盯着"和对照层的"对谁、在哪一步、按哪个按钮"都是动作。留着。
- **别往里加性格故事和形容词。** "格子""常见度"对审查员没用（对排优先级的人有用），可以不让审查员读。【推断】
- **"玩法画像"里有低知识角色的味道**（不读字、马虎、新手）。按 [T26][T24]，要防止模型把"他不懂"演成"我也不查"。2.1（1）和 2.4（3）的两段话就是为这个写的。
- **"觉得不对劲"那一栏是在给方向。** 它提高检出，也可能让审查员只盯这几处。评测时分开量（3.3 第 5 步）。
- **走法（故事外壳）比画像更能改变行为** [T30]。所以"加一种走法"通常比"加一个画像"更能带来新发现。上一轮把软锁、账本做成走法而不是画像，和这个结果对得上。【推断】
- **不要用画像来代表真实人群的看法**（会不会喜欢、会不会差评）。这一点上一轮已经说过。

## 五、各方向查到了什么

### 5.1 厂商的提示词和代理指南（Anthropic）

对"读很多文件、走很久、写带出处的报告"的代理最有用的几条：

- **说清楚、给理由。** 把模型当成聪明但不了解情况的新同事；规则后面写一句为什么，模型会自己推广 [T1]。
- **例子**：三到五个，贴近真实、互相有差别、用标签包起来 [T1]。别塞一长串边角规则，挑有代表性的例子 [T13]。
- **标签分块**：规矩、背景、例子、输入各包一层 [T1][T13]。
- **长材料放上面，要求放最后**；多份材料各包一层并带来源；先让模型摘出有关的原文再做事 [T1]。
- **角色**：系统提示里一句角色能定调子 [T1]。（准确度方面的研究见第四节。）
- **减少幻觉**：允许说"不知道"；先摘原文；写完逐条找支持的原文，找不到就撤；同一提示跑几次比对；只许用给的材料 [T3]。读代码的代理：没打开的文件不下结论 [T1]。
- **一致性**：写死输出格式；给例子；复杂任务拆成一串小任务 [T4]。要严格的 JSON 用结构化输出功能，无界面模式有 `--json-schema` [T4][T7]。
- **长任务**：告诉模型上下文会被压缩；状态存文件（结构化的用 JSON，进度用自由文字）；第一个窗口搭架子，后面的照清单做 [T1][T17]。
- **提前收工**：新模型在长任务里有时列出"还剩什么"就停；官方给了一段话，测试里未完成的结束少了约一半，输出多了约三成 [T2]。
- **别过度提示**：强调词、"要彻底"之类现在容易引起过头；"never"会被当成绝对规则；为旧模型写的谨慎条目要清理 [T2][T8]。
- **effort**：从 high 起步；medium 和 xhigh 在自己的评测上各试一次；effort 不怎么影响回话长短 [T2]。
- **子代理**：不继承主对话，只拿到系统提示、委派消息、CLAUDE.md 和环境信息；正文就是系统提示；工具要收紧；默认最多并行 20 个 [T6]。把同一个任务交给子代理不会让答案更好；有用的是并行、隔离噪音、和"没看过推理的新审查者" [T8]。
- **委派消息**要有目标、输出格式、工具和材料、边界 [T12]。子代理把成果写进文件、只回一个引用，避免转述走样 [T12]；回主代理的摘要控制在一两千 token [T13]。
- **多代理的代价**：代理大约是聊天的 4 倍 token，多代理约 15 倍；适合能并行、互不依赖的广度任务，不适合互相依赖多的任务 [T12]。
- **审查的现成流程**：并行找 → 单独验证滤误报 → 去重排序 [T9]；本地审查用 effort 换"覆盖面和把握"：低档只报最有把握的，高档铺开 [T10]；安全审查提示有硬排除清单、先例清单、每条发现一个并行过滤子任务、按 1–10 打分、低于 8 的不要 [T19]。
- **无界面模式**：`--append-system-prompt(-file)`、`--allowedTools`、`--output-format json`（带花费和会话 id）、`--json-schema`、`--bare`、`--resume` [T7]。
- **评审代理要调多疑**：默认偏松，会先指出问题再说服自己放过；靠例子和读日志反复校 [T16]。模型升级以后，把脚手架一件一件拿掉，看哪件还真的在起作用 [T16]。

### 5.2 角色扮演 / persona

见第四节。一句话：角色带来多样，不带来准确；动作清单比形容词管用。[T22]–[T31]

### 5.3 用模型找 bug / 做代码审查

- **误报是主要问题。** 一个千例的代码审查基准上，最好的工具 F1 不到两成，卡在精确率 [T41]。两个编码代理在真实网站项目上找漏洞，八成以上是误报 [T33]。三万多条机器审查意见里，一半以上被开发者拒了，主要原因是误报、重复、越界 [T42]。
- **不稳定。** 同提示同代码，多次运行结果不同 [T33][T39]；改个变量名、加点无关调用，模型就可能改口 [T39]。
- **上下文越大，越找不到。** 同一个已知漏洞，给三千行代码时一百次找到 8 次，给一万二千行时一百次找到 1 次 [T32]。
- **压误报的办法**：
  - 分阶段，先找后验 [T9][T19][T34][T44]。
  - 要证据：有的流程要求能复现的证明 [T44][T21]；我们做不到运行，只能要求"原文走通"。【推断】
  - 对抗式核对、信息不对等、判驳回要有代码依据 [T43][T44]。
  - 硬排除清单和先例 [T19]。
  - 静态分析出候选，模型裁决；或模型给静态分析补规格 [T36][T37][T40]。
  - 带"路径条件能不能成立"的验证器 [T38]。
- **漏报怎么办**：多个不同的提示并行看不同方面 [T11]；多跑几次取并集 [T33][T41]；先看历史上修过什么，再找类似的没修的 [T21]（对应到我们：`previousReviews` 里修过的问题，去别的角色身上找同一种）【推断】；提示从"保守"改成"看到可疑就查到底"，由后面的环节滤 [T34]。
- **松紧分工**：找的人放开，核的人收紧。同一个提示里又要"别漏"又要"别误报"，两头都做不好。[T34][T44]【推断】
- **强调"宁可不报也别误报"的提示**，在一个实验里仍然有不少误报 [T32]。说明光靠一句话压不住，要靠流程。

### 5.4 多代理流程

- **什么时候有用**：任务能拆成互不依赖的块；要并行；单个上下文装不下 [T12][T49]。我们的"每组一个审查员"属于这一类。
- **什么时候只是烧钱**：子任务互相依赖多、要共享上下文；单个代理已经够强 [T12][T48][T49]。一个对 260 种配置的对比里，多代理相对单代理从加八成到减七成都有，看任务结构 [T49]。
- **怎么失败**：十四种失败方式，三大类：系统设计、代理之间对不齐、任务核对 [T47]。并行的子代理各自带着没说出口的决定，合起来对不上 [T48]。
- **传上下文**：成果落文件、传引用 [T12]；代理之间用文件交接，开工前先约好"做完的标准" [T16]；一份结构化清单 + 一份进度笔记 [T17]。
- **规划者-执行者-评审者**：在长任务上有效，但贵（一个例子里从 9 美元到 200 美元）；模型变强后，中间的"分段"被拿掉了，规划和评审留下 [T16]。
- **辩论、评审团**：见 3.7。

### 5.5 长上下文和大代码库

- 相关信息在开头和结尾时用得最好，在中间时变差 [T51]。
- 对 18 个模型的测试：输入越长越差，简单任务也一样；一条相关但无用的干扰内容就能拉低准确度；同一个问答任务，只给有关的几百 token 比给全部十几万 token 好得多；不同家的模型坏法不同，有的倾向于不答，有的倾向于自信地答错 [T52]。
- 官方的说法两头都有：上下文很少用完了，不必为省而省 [T8]；但上下文是有限的注意力，越满越容易记错，要只放高信号的内容 [T13]。合起来：**不用怕读，但别把无关的东西留在里面**。【推断】
- 办法：先有地图再按需读 [T53][T13]；笔记写到上下文外面 [T13][T1]；子代理各用干净的上下文、回一个摘要 [T13]；快满时压缩，或干脆换一个新上下文从文件接着做 [T1][T16]。
- 对我们：每组审查员范围别太大（已经按角色拆分了，对）；走完一趟马上查候选；账本和覆盖表落文件。

### 5.6 输出质量

- **结构化输出**：强制 JSON 等格式会拉低推理 [T55]。先自由写、最后给结构化的一小块，或分两步。
- **引用原文位置**：官方的基本办法 [T3]。可以用脚本核（3.4）。
- **置信度**：口头置信度偏高；多次采样看一致性、换问法能缓解，没有哪一招通吃 [T54]。按证据分档比自评分数可靠。【推断】官方的安全审查提示用了打分加阈值，但打分的是另开的子任务，不是找的那个 [T19]。
- **说"不知道"**：明确允许 [T3]；给评判留"不确定"选项 [T15]。
- **例子怎么选**：贴近真实、有差别、三到五个 [T1]；评审代理用例子校松紧 [T16]；专家的"过 / 不过 + 评语"直接当例子 [T56]。一项工业研究说减误报时少样本提示在几种提示法里最好、"一步一步想"最差，这一句我只在搜索摘要里看到 [T40]。"反例管不管用"没找到专门的研究。
- **报告给谁看**：给没看过过程的人；结论先说；不用临时起的词 [T2]。

### 5.7 评测

见 3.3。补几条：

- 定义：一道题、一次尝试、打分器、记录、结果 [T15]。
- 打分器三种：代码的（快、死板）、模型的（灵活、要对着人校准）、人的（准、贵）。先用代码的，不够再用模型的 [T15][T5]。
- 模型打分：评分标准写细；让它先推理再给结论；用和被测不同的模型 [T5]；过 / 不过加评语，比 1–5 分好用；看"真问题判对的比例"和"非问题判对的比例"，别只看总一致率 [T56]。
- 看结果，不看路径：别要求代理必须按某个顺序做 [T15][T12]。
- 统计：报误差范围；同题配对比较；每题多采样几次再平均；先估算要多少题才看得出想看的差别 [T18]。
- 业界的基准大多是厂商自己做的，互相不一致，没有公认标准 [T58]。

## 六、没查到的、拿不准的

**关于证据本身**

1. **"只读作品、在脑子里玩"这套做法准不准，仍然没有外部证据。** 这一轮的数字几乎都来自代码审查和安全漏洞挖掘。搬过来都是推断。
2. **我读到的不全是原文本身。** Anthropic 文档站的几页（T1–T4、T7、T9、T10，T8 的几节）我读的是页面原文。别的网页（Anthropic 工程博客、别家博客、arXiv）是抓取工具打开页面后给我的转述，我没逐字看到原文。arXiv 的论文大多只打开了摘要页。第七节逐条标了。
3. **数字的可信度不一样。** [T20][T34][T44][T58] 是厂商或从业者自己报的，没有独立复核。[T43] 作者自己写明：单人操作、没有消融实验、没量漏报。
4. **几个年份没在页面上核对**：T15、T16、T56。
5. **[T40] 里"少样本最好、一步一步想最差"**只来自搜索摘要；摘要页没写这一句。
6. **[T31]** 只看到搜索摘要。

**关于具体做法**

7. **`omitClaudeMd` 字段**：只在子代理文档的字段列表里见到名字，没读到说明。子代理文档最后一段（约七分之一）抓取时被截掉，没读到。
8. **`--bare` 模式下 Grep / Glob 还在不在**：文档只说有 Bash、读文件、改文件工具。审查员要用 Grep。上之前要试。
9. **用钩子或权限规则把"只能写报告文件"变成强制**：官方说不能通融的规则该交给钩子或拒绝规则 [T8]，但我没读钩子文档，不知道能不能按路径限制 Write。
10. **`--append-system-prompt-file` 放一份很长的审查员说明**，和代理文件里的正文效果是否一样，没有测试。
11. **例子会不会被照抄。** 例子太像某一类问题，审查员可能只找这一类。官方说要有差别 [T1]。要在评测集上看：加例子以后，别的类型的检出有没有掉。
12. **清单 A–K 该不该移出系统提示**（2.1（5））。我拿不准。
13. **核对员默认留【可能】还是默认驳回**。我选了前者，理由是没有"运行"这个最后关口。如果【可能】堆得太多，{{OWNER}}看不过来，再往"驳回"那边调。要看评测和决定记录。
14. **核对员要不要换一家的模型。** 只有一篇从业者论文支持 [T43]，数字很小。
15. **作品地图在小作品上值不值。** 例子项目只有几个文件，地图可能比原文件还长。大概只对中等以上的作品划算。【推断】
16. **没查到的**：
    - 专门研究"审查提示里放反例（不该报的例子）"效果的论文。
    - 直接比较"动作清单画像"和"形容词画像"在**测试 / 找 bug**上的差别的研究（[T30] 是调查类文字游戏里的行为，不是找 bug）。
    - 大模型做**游戏剧情 / 任务逻辑**静态审查的评测（上一轮也没找到）。
    - 别家厂商的提示词指南这次没查，只看了 Anthropic 的。
17. **模型在变。** [T1][T2] 里有不少是针对某一代模型的说法（例："这一代容易提前收工""那一代容易过度验证"）。换模型以后，2.1（7）这类补丁可能不需要了，甚至有害。官方自己也说：照搬以前先在自己的评测上测 [T1][T2][T16]。
