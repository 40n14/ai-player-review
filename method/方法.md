# 玩家视角审查的方法

给谁用：主 AI，和主 AI 派出去的审查员。
干什么：只能读代码、设计稿、测试日志的时候，照**不同的玩家会遇到的样子**去走一个作品：他们会碰到什么问题、想要什么而作品没给、哪些地方做对了。不专查代码逻辑。
整套工具包的定位、原则、各部分怎么配，在`docs/design.md`。这一份讲方法的道理和每类问题怎么查。

说法：被审查的东西叫「作品」（游戏或模组）。模组依附的游戏叫「宿主游戏」；作品是独立游戏时，读成"作品里原有的系统"。拿主意的人叫「负责人」。

干活用的在别处：画像库 `method\画像*.md`（索引 `method\画像_索引.md`）加项目对照层（项目设置的 `personaOverlay`）；走法 `kinds\kinds.json` 和 `kinds\<id>.md`；审查员、核对员的提示词 `agent\`；合并说明 `skill\player-review\merge.md`；静态表 `static\run_all.py`。

来源编号 [M1]… 在`docs/references.md`。引用都是转述。

## 一、一页纸用法

1. **定这次看谁**：改动过的角色，加上会和他们互相提到的。不是第一轮：上一轮说要修的一定在范围里（`决定记录.csv`）。
2. **跑静态表**。文字问题多数在这一步能定。
3. **建作品地图**（`kinds\map.md`）：线、选择点、标记、东西、结局、数值、文本、牵连，每行带出处。后面的人都读它。
4. **派审查组**：照项目设置的 `reviewGroups`。每组的 `kind` 定走法：`persona` 组扮演画像；别的组（软锁、经济、想要的选项、事实账本……）按表或清单走。`reviewFocus` 是这次的重点。
5. **走**：先把要走的每一趟列进草稿，再一趟一趟走。每一步问：玩家此刻知道什么、想做什么、以为会怎样、实际怎样。不对劲的先记成候选。
6. **查**：每条候选反过来查（找挡住它的条件）、走到底（一直走到存档、读档、过回合以后）。
7. **对清单**：第四节。
8. **写报告**：玩家反馈（每句挂证据）、问题、想要但没有的、要负责人定、查过没问题的、没走到的、索引。把握照第六节标。
9. **核**：脚本核引文；每条主张派一个核对员，他不看审查员的推理。
10. **合并**：筛掉不该报的，合并同一根源的，对账，汇总玩家反馈。
11. **交给负责人定**，把决定记下来。要运行才能确认的：写出测试步骤，先不跑，何时跑照项目规矩（`rulesFile`）。

## 二、为什么要玩家视角

代码审查拿代码对设计稿。玩家拿眼前看到的东西对自己的常识。

**走流程才看得见的问题（常见的几种）**

- 每段代码各自都对，可玩家把一件事做了一半，人物就来了，再做完：中间那一幕整个丢了，没有报错。
- 一句话，一趟看没问题；连着看五趟，才发现每趟都说。
- 代码没错，是选项提示把结局说给了还没见过这个人的玩家。
- 玩家早早关了店，一句"只说一次"的话永远丢了。

**别人的例子**

- 《博德之门 3》：一个同伴约 1500 句台词因为 bug 不触发，是编剧发现台词不见了才去查的 [M16]。
- 《质量效应 3》：从前作导入存档时，部分自定义的脸导不进来 [M17]。老存档是开发者很少走的路。
- Failbetter 做《Mask of the Rose》时说：严重的 bug 常出在技术和文字接起来的地方 [M8]。
- 软锁的定义：玩家被困住了，但程序没有崩 [M19]。

**结论**：玩家视角补三样。**顺序**：先做什么后做什么。**时间**：连着好几趟、隔了几天、跨了版本。**只看得见的东西**：台词、按钮、物品、钱、弹窗。

## 三、借来的方法

| 方法 | 出处 | 借来干什么 |
|---|---|---|
| HTSM（启发式测试策略模型） | [M2] | Operations 里有"不受欢迎的用法"：无知、出错、粗心的人的输入。Time 里有快慢、打断、并发。→ 画像和打断清单的骨架 |
| FEW HICCUPPS 判定法 | [M1] | 没有完整设计稿时怎么判断"是不是错"：和**以前的版本**比（History）、和**作品里同类的东西**比（Product）、和**世界设定**比（World）、和**自己说过的话**比（Claims：说明、选项提示、商店页）、和**玩家合理的期待**比（User desires）、玩家**能不能自己解释**（Explainability）。作者说这些判定会出错、要看场合，只是提示"可能有问题" |
| 测试"旅行" | [M3] | 每次选几条路线：**破坏者**（专找会坏的用法）、**下雨天**（中途取消、打断）、**博物馆**（老代码、上一版：就是老存档）、**导游书**（照说明书做）、**快递**（跟着一样东西从头走到尾）、**下班以后**。再加"冷门路线"：关掉部分内容、无尽模式、别的语言 |
| 按时段的探索测试（SBTM） | [M4] | 每个画像跑一遍 = 一个时段：开头写一句任务，结尾写简报。不追求一次查完 |
| ChoiceScript 的 Quicktest / Randomtest | [M5][M6] | 两种互补的自动测试。**每个分支走一遍**：会报出玩家走不到的假 bug。**随机玩很多遍**：只报真能遇到的，但要很多遍；还能数每句台词走到几次，0 次是可疑的死台词。两种各能找到对方找不到的 |
| Ink-Tester | [M7] | 随机跑几千遍，输出每句台词的覆盖次数。只知道到没到过 |
| Failbetter 的随机跑本器 | [M8] | 随机选择不像人，他们打算加"玩家画像"引导电脑玩家。→ 画像长跑（第七节） |
| 把剧情当程序编译检查 | [M9][M10][M12] | 控制流图、符号执行可以证明"某段对话永远走不到"[M9]。Yarn Spinner 的 Story Solver 用定理证明器找软锁、走不到的内容（封闭测试中）[M10]。也有人用模型检验查冒险游戏的场景能不能到达 [M12]。→ 静态流程表的上限，先做便宜的一半 |
| Inform 7 的 Skein | [M11] | 把一次游玩的文字记下来"认可"，以后每次改动重放、比对，不一样就标出来。→ 认可过的来访记录 |
| 规则库对话（Valve） | [M13] | 每句台词挂条件，从最具体的规则往通用的退。典型错误：条件少一个、"说过"记早了、两条规则同时成立时选错 |
| 质量 / 显著性叙事（storylet） | [M14] | 一次来访 = 一个小故事，靠状态解锁、按条件挑。查的重点是状态：谁写、谁读、什么时候写 |
| 《哈迪斯》的对话 | [M15] | 写大量台词是为了在循环里少重复；支线能从很多方向进入，游戏要记住玩家做过什么。编剧说脚本多数简单，但也有不简单的时候。（"按优先级排对话"没找到一手资料，不引用。） |
| 画像代理 | [M20][M21] | 用几种典型的决策风格代表不同玩家 [M20]；给 LLM 测试代理加不同性格，同样情况下走不同的路，覆盖更多 [M21] |
| LLM 测试代理 | [M22][M23] | TITAN：把游戏状态压成文字、记住做过什么、用 LLM 当判定器 [M22]。更早的研究：把一串**文字写的游戏事件**交给 LLM 找哪件不对，最好约七成准 [M23]。→ 测试日志适合让 AI 读 |
| LLM 的短板 | [M24][M25][M26] | 看截图找画面错误还很吃力 [M24]：画面要人看。代码审查类工具不够准，几次合起来明显变好 [M25]：→ 派几组再合并。模拟用户比真人一致 [M26]：→ 粗心、反复、半途而废要在提示里**明确要求** |
| 大模组装进老存档 | [M27] | 一个大型模组合集的说明：装进进行中的存档可能弄乱任务标记；删模组前要先清掉它加的东西。→ "半路装""删掉再装回"两个画像 |
| 游戏论坛里的真实报告（作品是模组时，看它依附的那个游戏的论坛） | 例 [M29] | 去论坛看玩家真的报了什么。例：有人报换电脑后模组全变回"未批准"；有人报长局第 211 天开不了店。→ 玩家可能有几天没开这个模组；长局要查 |

## 四、每类问题怎么查

每条是一个**问题**加**怎么查**。文件在哪看项目设置：源码 `modSource`，人物数据 `characterDir`，行为代码 `behaviourDir`，文本表 `csv`，设定集 `loreBible`，测试入口 `testRunner`。

### A. 进度、卡死

| 问题 | 怎么查 |
|---|---|
| 有没有一种玩法，让一条线永远不结束、也不推进，一直占着名额？ | 行为代码里"这条线完没完"的判断和每个推进条件。逐个问：玩家一直不做会怎样。信号：没有超时，没有放弃的出口 |
| 推进要的东西，玩家可能已经没有了吗（卖了、被偷、被清掉）？ | 列出每个"要玩家拿出东西"的地方，问：东西没了走哪条路 |
| 按钮只在某个状态下出现，这个状态会不会永远到不了？ | 从按钮条件倒着找"谁把它写成真"。找不到 = 死按钮 |
| "等玩家做 X 才往下"，界面上告诉过玩家吗？ | 文本表里那几句台词：提示够不够猜到 |
| 人物被停用、被关掉、没被抽中时，这条线让位吗？ | 管名额和排期的框架代码 |
| 一个人没了（死、被抓、离开），后面等他的人会不会一直等？ | 后续人物的触发条件。日志每天重复同一句"在等"是信号 |
| 测试靠调试快捷键到的状态，玩家不用它能到吗？ | 测试场景是不是都"直接叫人、直接跳天" |

### B. 台词和状态对不上

| 问题 | 怎么查 |
|---|---|
| 第一次来会不会说"上次 / 又 / 老样子"？（例：一个开店游戏里，客人说"老样子"，可这是他第一次来） | 在文本表里搜这类词，逐条看挂在哪种来访、什么条件下。静态表有台词连续性一张 |
| "只说一次"的话，是真显示了才记，还是排上队就记？ | 写"说过了"的那行在显示之前还是之后。走法：人排上了，玩家关店，下一趟还说不说 |
| 该说一遍的话，说了好几遍吗？ | 条件里有没有"说过就不说"。连走几趟，数次数 |
| 台词说的事和玩家做的对得上吗（谢你让价，可你没让）？ | 条件读哪个状态；它是这一趟写的，还是很久以前写的 |
| 台词里的时间和真实隔的天数对得上吗（"好久没见"）？ | 条件里有没有天数判断 |
| 两句有先后的话，会不会先说后一句？ | 后一句的条件能不能单独成立 |
| 和这一局的世界状态矛盾吗（大事已经结束，他还当它在进行）？ | 条件有没有看宿主游戏的状态；对设定集 |
| 人物知道他不该知道的事吗？该知道的却不知道吗？ | 条件读的是"玩家做过"还是"他看见过" |
| 许诺了以后（"下周再来"），兑现了吗？没兑现有交代吗？ | 列出带许诺的台词，逐条找兑现的代码 |

### C. 东西和钱

| 问题 | 怎么查 |
|---|---|
| 人物给的东西放到哪？位置满了、玩家没答话就拿走，怎么办？ | 给东西、拿回东西的代码；有没有"放不下"的分支 |
| 剧情物品会不会被宿主游戏清掉、偷走、没收？ | 列出宿主里所有会让物品消失的系统，逐个对 |
| 能不能白拿（拿了没付钱）或白丢（付了钱没东西）？ | "拿回 / 付钱"两步之间能不能被打断 |
| 一样东西从出现到消失，跟着走一遍 | 每一步归谁、在哪、图和说明对不对 |
| 人物的钱够买吗？他付的钱、给的东西合理吗？ | 人物数据里的预算字段，对宿主的物价 |
| 违规交易：宿主算一次，作品又算一次，有没有重复或漏算？ | 设定集里的规则；作品里掷骰、记账的代码 |

### D. 时间和排期

| 问题 | 怎么查 |
|---|---|
| 他最早能来那天，玩家做得了他要的事吗（有货、有钱、有工具）？ | 人物数据里的最早日子；跳没跳教学都算 |
| 他该来那天店没开：顺延、丢掉，还是第二天挤两个人？ | 排期的框架代码 |
| 作品里两个人同一天来：顺序、互相提到、抢同一个位置 | 造客人、排队的代码 |
| 定期抽选：弹窗没答、那天没开店、所有线都走完了，各会怎样？ | 抽选的代码和对应的日志 |
| 主线走完后的来访：太早、太密、永远不停？ | 主线后来访的间隔字段 |
| 宿主游戏的事件期间，他来吗、说什么？ | 事件来访的数据和条件 |

### E. 存档、读档、旧存档

| 问题 | 怎么查 |
|---|---|
| 哪些东西写在存档外面（设置、"看过"标记），会和存档对不上？ | 找写设置文件、不写存档的代码 |
| 读档后的"往前推"：只做一次吗？有没有跳过一幕或重演一幕？ | 各人物读档时跑的那段；每个阶段都走一遍 |
| 新加的存档字段老存档里没有：默认是"没发生"还是"已发生"？ | 读字段的地方的默认值；哪个对玩家合理 |
| 物品的图、大小、id 改了：老存档里的东西读档后怎样？ | 物品定义的改动；读档修补的代码 |
| 删掉作品读档、再装回来：说明里承诺的事是真的吗？ | 说明里讲存档的那一段，对代码 |

### F. 界面文字和剧透

| 问题 | 怎么查 |
|---|---|
| 选项、设置页里的名字和说明，有没有说出身份、关系、结局？ | 文本表里选项提示、标签几类键；用"从没见过这个人"的眼光读 |
| 标着"占位 / 待改"的文字，哪些玩家这个版本就会看到？ | 文本表的占位段；发布前列给负责人 |
| 说明、商店页里说的事，和代码一样吗（数量、上限）？ | [M1] 的 Claims；静态表可核对写明的数字 |
| 发布版里还有调试痕迹吗（调试按钮、"（草稿）"、测试台词）？ | 打包脚本的产物 |

### G. 数字手感

| 问题 | 怎么查 |
|---|---|
| 照"好心人"玩几趟走完主线？照"精明生意人"玩几趟人就没了？ | 人物数据里的门槛（好感、次数、天数） |
| 一个"可能出事"的掷骰，一局碰到几次？出事前有提示吗？ | 百分比 × 来访次数，估期望 |
| 藏起来的数（好感、声望），玩家感觉得到吗？ | 不同数值下的台词有没有差别 |

### H. 人物之间互相提到

| 问题 | 怎么查 |
|---|---|
| 被提到的人，这一局玩家见过吗？ | 条件要分清"来过以后走了"和"从没来过" |
| 被提到的人现在的状态，和说的话一致吗（死了、只是不来）？两个人说同一件事，说法一致吗？ | 条件有没有看结局的种类；并排读两人的台词 |
| 一个人的结局，会让另一个人的线卡住或跳过吗？ | 跨人物的标记：谁写、谁读；读的人处理了"没写"吗 |

### I. 别的模组

| 问题 | 怎么查 |
|---|---|
| 作品改宿主行为的地方，别的模组也改会怎样？ | 作品列出的补丁点；改不上时有没有提示 |
| 别的模组的人物，会不会占作品的名额？ | 作品靠什么认"自己的人" |
| 别的模组改了容量、数量，作品的假设还成立吗？ | 找写死的"多大""几个" |
| 作品被关了一段时间又开回来 [M29]？ | 同"半路装"的画像 |

### J. 多语言

| 问题 | 怎么查 |
|---|---|
| 各语言文本表的键、占位符对得上吗？ | 静态表的文字检查 |
| 译文意思一样吗？有没有多说（性别、年龄、名字）？ | 两种语言并排读 |
| 译文放得下吗？叫法统一吗？ | 长度能算，按钮和弹窗要截图；叫法对设定集 |

## 五、交互 bug 怎么查

**是什么**：作品的物品、人物、按钮，碰到**宿主游戏的界面和系统**时出的问题。顺着剧情读代码找不到，因为问题在剧情没提到的宿主窗口里。

例：模组加的一件物品，在宿主的某个选择窗口里画成"?"。那个窗口按图名回宿主的图集重新取图，取不到。物品在作品自己的代码里处处都对。

### 1. 列一张「作品的东西 × 宿主的界面和系统」的表

静态表的交互表给出底稿，行和列在项目设置里配。

每件东西先问一句**玩家的手够得着吗**：点得中、拿得起来、拖得到剧情要它去的地方吗。审查员不看图，所以靠自带的图片表（`_image_hits.md`：每张图有多大一块是不透明的），再回代码查游戏按什么判定点中。例：一件剧情物品的图只有一小块点得到，游戏又按像素判定，玩家拿不起来、放不到剧情要它去的地方，那条线就走不下去；读剧情和代码都看不出来。

**物品这一边**：行 = 作品的每件物品。列 = 宿主里物品会去的每个地方：

| 界面 / 系统 | 要问的 |
|---|---|
| "选一件"的窗口 | 会不会被列出来；图是自带的，还是按名字重新取的 |
| 容器、仓库 | 能不能放、能不能套着放；放进去以后作品还找不找得到 |
| 展示、售卖 | 标多少钱、会不会被买走；卖掉以后剧情要的东西没了 |
| 说明面板 | 说明是不是作品写的；有没有露出 id 或空字 |
| 拆、修、充能、加工 | 能不能做；宿主按 id 认的东西，新物品 id 不同 |
| 偷、没收、过夜清理 | 没保护的剧情物品会不会没了 |
| 排序、堆叠、旋转 | 叠在一起以后各自的标记丢不丢；转过来判定对不对 |
| 存读档 | 图、形状、标记、位置，读档后还在吗 |
| 配方、别的模组 | 会不会被当成材料；别人按标签找东西时会不会算上它 |

**人物这一边**：行 = 宿主的每个系统，每个人物走一遍。例：排队、报警或举报、检查人员在场、开关店、宿主的事件、宿主和作品的按钮同时出现。

### 2. 每一格问三件事

1. **玩家看到什么**：图（是不是"?"、大小对不对）、名字、说明、价钱、按钮上的字。
2. **能不能做宿主允许的每个操作**：拿起、放下、旋转、放进容器、卖、拆、丢。宿主对同类东西允许的，作品的东西也该允许；不允许要有道理。
3. **做了以后作品知不知道**：卖掉、拆掉、被偷、读档以后，剧情还认不认这件东西；人物被宿主系统带走以后，作品的状态对不对。

### 3. 哪些读代码能定，哪些必须看画面

**读代码能定的**（写【确定】）：

- 宿主怎么取图：**另外**按名字重新取图、或新造一件物品的地方，作品的图会丢。
- 宿主怎么判断能不能放、能不能用：按标签、按 id，还是按图的形状。
- 宿主怎么算价：照宿主某件东西做的，价钱和类型多半是那件的。
- 宿主按 id 重造一件的地方：作品加在"这一件"上的标记会丢。

**必须看画面的**（写【可能】，加测试步骤和截图清单，先不跑）：图长什么样；字放不放得下；按钮叠不叠；某个系统进行时按钮出不出。

```
测试：<场景名>
步骤：拿到这件物品 → …… → 打开那个窗口
截图：窗口整窗；鼠标停在物品上的提示
检查：图是哪张；形状多大；名字是什么
```

### 4. 怎么走

这是一个审查种类（`interaction`），和画像走查并列。不扮演性格：

1. 先看交互表里标出的可疑处。每条回宿主代码看一遍，定【确定】/【可能】/ 不是问题。写了"作品已处理"的，去看是不是真的盖住了。
2. 再一格一格走：每件物品 × 每个界面，每个人物 × 每个系统，都问三件事。空白的格也想一下：玩家会不会把它拿到那里。

## 六、报告和把握

**一条问题写成一小段**：怎么遇到（玩家一天一天的操作）、玩家看到什么、为什么不对（对照的是什么，见 FEW HICCUPPS）、出处、反查、建议、测试步骤。格式在审查员说明里。

**把握分三种**

- 【确定】：读代码和文本就能定，写得出是哪一行造成的。
- 【可能】：要看画面、要运行，或者牵涉没读到的宿主代码。必须带测试步骤。
- 【设计】：实现和设计稿一致，但玩家多半会觉得不对。不是 bug，要负责人拿主意。

**为什么这样分**

- AI 只读不玩，会误报；判定法本身也会出错 [M1]。所以每条都要反查，并说清把握。不分把握，读的人只能全信或全不信。
- AI 看不了画面 [M24]。画面上的事一律写【可能】。
- 一次审查不够准，几份合起来好得多 [M25]。所以派几组再合并。
- "查过、没问题的"和"没走到的"也要写：下一个人靠它知道哪条路走过了。

## 七、能做成程序的部分

- **画像长跑 + 来访记录**：测试入口按画像的规则表一天一天自动玩，固定种子 [M5]；每趟来访记成玩家看到的样子，改动前后比 [M11]。能抓跨很多天的问题。几个种子不等于全部情况 [M6]。
- **静态表**：只读文件。每句台词在哪用、挂什么条件；死键、缺键；只写不读的标记；带"上次、又"的台词能在第几次来访说。只知道"用到了"，不知道"走得到"，会有假报 [M5]。

配合：先代码审查（实现错），再玩家视角审查（体验、顺序、跨天的错），最后整轮测试。每个问题修好，补一个按玩家步骤写的测试。
