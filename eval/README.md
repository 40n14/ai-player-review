# 评测：改了以后是变好还是变坏

改提示词、换模型、加一个环节，都可能让审查员变好，也可能变坏。不量就只能凭感觉。这个文件夹是量的办法。

**审查员不许读这个文件夹**（例子项目的 `neverRead` 里有它）：里面是答案。

## 有什么

- `tea-stall\answers.json`：例子游戏「茶摊」的答案表。埋进去的真问题（`issues`）、缺口（`wants`：玩家想要、作品没给的选项）和诱饵（`decoys`：看着像问题、其实不是的，报了算误报）。
- `score.py`：打分。读每份报告最后的「索引」，对着答案表算：每个问题几轮里找到了几轮、诱饵被报了几次、哪些发现对不上答案表。
- 评测用的项目设置是 `examples\tea-stall\project.eval.json`：和 `project.json` 一样，只是画像对照层换成了没有「觉得不对劲」「去查」的版本。原版的对照层几乎把答案指给了审查员；两版都跑，差出来的就是"对照层写得细"值多少。

## 怎么跑

1. 同一个配置**至少跑三次**（同一份提示跑几次，找到的东西并不一样）：

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File api\player_review_api.ps1 -ProjectFile examples\tea-stall\project.eval.json -Parallel -OutDir <某处>\run1
   # run2、run3 同样
   ```

   这是真的调 API，花钱。例子很小，一轮比真项目便宜得多；第一次先跑一轮看花费表。
   上一轮的输出文件夹别放在审查员读得到的地方（`review_out_eval` 用完挪走，或者 `-OutDir` 写到项目外面）。

2. 打分（不花钱）：

   ```powershell
   python -I eval\score.py --answers eval\tea-stall\answers.json --out <某处>\score.md <某处>\run1 <某处>\run2 <某处>\run3
   ```

3. 人看一遍：
   - 「对不上答案表的」：没埋但真的问题，补进答案表；剩下的才是误报。
   - 抽几条"找到了"的：是不是真说到了点上（打分是按文件名和词粗配的）。
   - 没找到的：翻报告和草稿，看是审查员的错，还是题出得不好。

4. 比两个版本：同一批题、逐题比。题少的时候只看得出大差别，差一两题不要当真。

## 这个评测量不到的

- 例子太小、没有代码：量不到长文件、大作品下的表现，量不到对宿主游戏的猜测。小而干净的题会高估表现。
- 题目偏文字和数据；软锁、数值、存读档的题还少。要加题：改例子游戏，同时改答案表。
- 最真的数据是负责人对每条发现的决定（技能第 7 步的 `决定记录.csv`）：攒到几十条，算"报出来的有几成是真的"。
