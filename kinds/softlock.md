# 走法：软锁 / 卡死（softlock）

**抓什么**：玩家走不下去了，游戏却没坏：必须用的东西没了、必须见的人不来了、每个出口都被条件挡住、在等一件永远不会发生的事。后果最重，而标记和条件都写在代码和数据里，只读代码最能下结论。

**不扮演性格。** 组里配的画像（马虎的、对着干的、反复读档的）只提醒你玩家会怎么把东西弄没。

出处和依据：`{{KIT}}\method\调研_审查种类.md` 3.1。 来源列表在 `{{KIT}}\docs\references.md`（编号 K 开头）。

## 怎么走（先列清单再走，不要边想边走）

1. **列必经点**：范围内每条线、每个结局必须经过的事件、物品、角色、标记。有作品地图时从它的「结局和必经点」「标记和状态」「东西」三张表起步，再回原文件核对；没有地图再自己列。项目设置有 `invariants`（不变量，例"没钥匙不能通关"）的，一条一条都算必经点的判定标准。
2. 每个必经点写**它需要什么**：前置标记、物品、钱、某个角色在场、某个回合之前。
3. 每个"需要什么"，列出玩家**把它弄没**的全部办法：卖掉、送掉、用掉、弄死、赶走、错过那一回合、选了排斥它的选项、在中间存档读档、关掉相关内容、背包满了没拿到、东西就在那儿但点不中拿不起来（图大半是透明的，游戏又按像素判定：有静态表 `_image_hits.md` 就看它）。
4. 弄没以后：有别的路吗？有提示吗？会补发吗？
5. 查**只进不出**的状态：对话、菜单、小游戏里，有没有一种情况是每个出口都被条件挡住（例：每个选项都要钱，玩家没钱）。
6. 查**等不来的事**：某个标记在等一个事件，这个事件的触发条件能不能永久为假。占着位置的线（同时只能进行几条）特别要查。有标记读写表（作品地图或静态表里）时先看两类：有地方读、没地方写的标记；只有一处给、有多处能拿走的剧情物品。每一条都要回原文件下结论，不能只凭表。
7. **回头验这条路**：每条要报的"弄没 → 卡住"，把玩家的每一步列出来，每一步写它要的条件（`文件:行` + 原文）。这些条件能不能在同一局里同时成立？例：要"第 3 回合卖掉钥匙"，就要确认第 3 回合钥匙已经在手上、而且卖东西的按钮对它是亮的。有一步的条件不成立：这条不报，写进「查过、没问题的」。

## 每步问什么

- 这个条件查的是"做过那件事"，还是"手上有那个东西"？
- 玩家没钱 / 没货 / 没这个角色时，这一步还剩什么可选？
- 这条死路是作者故意的吗？有没有哪句文本在事先警告？

## 定把握

- 标记和条件写明的：【确定】。
- 宿主游戏可能有兜底（丢了任务物品会补发）、而作品的代码里看不到的：【可能】，写明要查宿主的哪一处。
- 看起来是故意的死路（坏结局）：不当 bug 报，放进「要{{OWNER}}定」，写"请确认是不是故意；玩家事先有没有提示"。

## 报告里多写什么

每条：必经点 → 弄没的最短步骤 → 卡在哪（`文件:行`、标记名）→ 有没有提示 → 把握 → 是主线卡死、支线卡死，还是只是亏了。
开头放一张必经点表：必经点｜需要什么｜能弄没吗｜弄没以后。没走完的必经点写进「这次没走到的」。状态太多走不完时：先主线，再各条支线。
